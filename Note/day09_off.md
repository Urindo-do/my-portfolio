## 1. INMP441 마이크 — 디지털 센서와 I2S

### 배선

| INMP441 | ESP32-S3 | 역할 |
|---|---|---|
| VDD | 3.3V | 전원 (3.3V 고정) |
| GND | GND | 0V 기준점 |
| SCK | GPIO 6 | 비트 클럭 — "지금 1비트 읽어" 박자 |
| WS | GPIO 5 | 워드 셀렉트 — 좌/우 구분 |
| SD | GPIO 4 | 실제 소리 데이터 (마이크 → ESP32 단방향) |
| L/R | GND | GND에 묶어 Left 채널로 고정 |

### 배운 것 — 아날로그 센서와 무엇이 다른가

Day 2의 조도센서는 ESP32가 **전압을 읽어 숫자로 바꿨다**(ADC). 그런데 INMP441은 **마이크가 이미 숫자로 바꿔서 보낸다.** 그래서 필요한 게 변환이 아니라 **약속(I2S)** 이다.

숫자는 통째로 오지 않고 **1비트씩** 줄줄이 오기 때문에, 데이터선(SD) 하나만으로는 부족하다.

- **SCK** 가 없으면 → 언제 읽어야 할지 몰라 값이 뒤엉킨다
- **WS** 가 없으면 → 좌우가 섞여 엉뚱한 값이 나온다

코드에서 `I2S_MODE_MASTER`는 **박자를 ESP32가 만들어 마이크에게 준다**는 뜻이다. 마이크는 그 박자에 맞춰 데이터를 내보내기만 한다.

### 오디오 기준값과 그 의미

| 항목 | 값 | 뜻 |
|---|---|---|
| 샘플레이트 | 16,000Hz | 1초에 소리를 16,000번 측정 |
| 비트 깊이 | 16-bit | 값의 범위가 -32,768 ~ +32,767 |
| 샘플 1개 | **2바이트** | 16비트이므로 |
| 1초 분량 (모노) | 32,000바이트 | 16,000 × 2 |
| 5초 녹음 | **160,000바이트** | 실제로 수신한 그 숫자 |

### 코드에서 가장 헷갈렸던 줄

```cpp
for (size_t i = 0; i < bytes_read / 2; i += 2) {
```

**숫자 2가 두 번 나오지만 뜻이 완전히 다르다.**

- `bytes_read / 2` — 바이트 개수를 **샘플 개수**로 바꾸는 나눗셈 (샘플 1개 = 2바이트)
- `i += 2` — **Left 채널만 골라내는** 건너뛰기

메모리에는 `Left, Right, Left, Right...` 순으로 번갈아 저장된다. L/R을 GND에 묶었으니 이 마이크는 왼쪽 전용이고, 오른쪽 슬롯에는 의미 없는 값이 들어온다. 그래서 **짝수 인덱스만** 취한다.

### DMA 버퍼는 왜 있나

```cpp
.dma_buf_count = 8,
.dma_buf_len = 1024,
```

소리는 **쉬지 않고** 들어오는데 CPU는 다른 일도 해야 한다. **DMA(Direct Memory Access)** 가 CPU를 거치지 않고 하드웨어가 알아서 메모리에 소리를 쌓아둔다. 버퍼 8개를 돌려쓰므로 CPU가 조금 늦어도 소리가 끊기지 않는다.

**중요**: 반대로 **꺼내는 속도가 쌓이는 속도보다 느리면 버퍼가 가득 차고, 그 다음 소리는 덮어쓰기되며 사라진다.** 유실의 실제 발생 지점은 마이크가 아니라 여기다.

## 2. 왜 시리얼 속도를 2Mbps로 올렸나

수업 코드에 `Serial.begin(2000000)`이 있었다. 기본값 115200이 아닌 이유를 계산해봤다.

UART는 1바이트를 보낼 때 시작·정지 비트가 붙어 **총 10비트**를 쓴다.

| 속도 | 초당 전송 가능량 | 필요량(모노 16kHz) | 판정 |
|---|---|---|---|
| 115,200 | 11,520바이트 | 32,000바이트 | **2.8배 부족** ❌ |
| 2,000,000 | 200,000바이트 | 32,000바이트 | **6.25배 여유** ✅ |

5초 녹음(160,000바이트)으로 보면 더 명확하다.

| 속도 | 전송 소요 시간 |
|---|---|
| 115,200 | **약 13.9초** ← 녹음 5초인데 전송이 3배 |
| 2,000,000 | **약 0.8초** |

### 여기서 확장된 개념 — QoS

> **대역폭이 유한하면, "무엇을 버릴지"를 먼저 정해야 한다.**

버릴 것을 정하지 않으면 시스템이 **아무거나** 버린다. 그게 하필 중요한 데이터일 수 있다.

지금 만든 시스템 안에 성질이 정반대인 두 데이터가 공존한다.

| 데이터 | 늦게 도착하면? | 필요한 보장 |
|---|---|---|
| **오디오 샘플** | 0.5초 늦은 소리는 **이미 쓸모없음** | 유실 허용 (Best-effort) |
| **로봇팔 각도 명령** | 놓치면 **엉뚱한 자세에 멈춤** | 반드시 도달 (Reliable) |

판단 기준은 "중요한가"가 아니라 **"늦은 데이터가 여전히 가치 있는가"** 다.

ROS2에는 이걸 설정으로 선언하는 **QoS(Quality of Service)** 가 있고, 센서용 프리셋(`sensor_data`)이 정확히 `BEST_EFFORT + KEEP_LAST` 조합이다. 지금 DMA 버퍼가 넘치면 덮어쓰는 동작이 같은 철학이다. **어쩔 수 없는 타협이 아니라, 데이터마다 필요한 보장 수준이 애초에 다르다는 것을 인정하고 의도적으로 다르게 설정하는 것**이다.

## 3. STT — 음성을 텍스트로

```python
import speech_recognition as sr

recognizer = sr.Recognizer()
with sr.AudioFile("user_voice.wav") as source:
    audio = recognizer.record(source)

text = recognizer.recognize_google(audio, language="ko-KR")
print("인식 문장:", text)
```

- Google Web Speech API 호출이므로 **인터넷 연결 필요**
- 입력은 앞 단계에서 PCM으로부터 복원한 `user_voice.wav`

### ⚠️ 막혔던 부분 ① — `ESP32 응답 없음`

```
🔴 녹음 중 [████████████] 5.0/5.0초
오류 발생: ESP32 응답 없음 — 보드 연결·COM 포트·펌웨어를 확인하세요.
```

**해결 과정 (시행착오 순서대로)**

1. COM 포트를 바꿔봄 → 해결 안 됨
2. 아두이노 IDE 설정을 바꿔봄 → 해결 안 됨
3. 포트를 다시 연결한 상태에서 시도하니 **전송되는 것을 발견** (COM6에서 정상)
4. 그런데 이번엔 **음질이 나빴음**
5. **마이크(센서)를 교체** → 해결

**얻은 것**: 증상이 "응답 없음"이라 통신 문제로만 보였지만, 실제로는 **통신(포트) + 부품(마이크 불량) 두 가지가 겹쳐** 있었다.
※ 어제 서보 "지지직" 문제도 **서보 불량 + 체결 과조임**이 겹친 케이스였다 — **이틀 연속 같은 패턴.**

> **규칙으로 정리**: 하나를 고쳤는데 증상이 남으면, 그건 "안 고쳐진 것"이 아니라 **원인이 하나 더 있는 것**이다.

## 4. LLM 연결 — 텍스트를 의도로

STT 결과를 Gemini에 넘겨 **정해진 형식의 JSON**으로 받는다.

```
STT 텍스트 → 프롬프트(instruction으로 JSON 강제) → Gemini
  → JSON 파싱 → emotion · action · reply 추출
```

### 정상 동작 로그

```
STATE: LISTENING
🎤 지금부터 5초간 말씀하세요!
🗣 인식 문장: 앞에 거 잡아
STATE: THINKING
🤖 emotion=HAPPY action=GRAB reply=네, 앞에 있는 물건을 안전하게 잡겠습니다! 잘 지켜봐 주세요.
```

"앞에 거 잡아"라는 자연어를 **`action=GRAB`** 이라는 로봇 명령으로 변환했다. 어제 만든 로봇팔과 연결할 수 있는 형태다.

### 인상 깊었던 부분 — 방어 장치들

LLM은 **매번 같은 형식으로 대답한다는 보장이 없다.** 그래서 코드에 방어 장치가 겹겹이 들어가 있었다.

| 장치 | 하는 일 |
|---|---|
| **instruction으로 JSON 강제** | 자유 문장이 아니라 정해진 스키마로 응답받게 함 |
| **재시도(retry)** | `ask_robot`에서 실패 시 다시 요청 |
| **검증 단계** | 형식이 깨지면 한 번 더 검사 |
| **허용 값 + 폴백** | emotion·action이 목록 밖이면 `NEUTRAL`/`NONE`으로 치환 |
| **마크다운 백틱 제거** | LLM이 ` ```json ` 으로 감싸 보내는 경우가 많아 `parse_llm_response`에서 벗겨냄 |

### JSON이 깨질 때 원인 좁히는 순서

| 순서 | 확인할 것 |
|---|---|
| 1 | `.env`의 `GEMINI_API_KEY` 오탈자 / `503 UNAVAILABLE`이면 무료 티어 서버 혼잡 → 재시도가 도는지 확인 |
| 2 | `print(response.text)`로 **Gemini가 실제로 보낸 원문**을 눈으로 확인 |
| 3 | 마크다운 백틱이 섞였는지, `parse_llm_response`가 제대로 제거했는지 |
| 4 | emotion·action이 목록 밖 값이라 `NEUTRAL`/`NONE`으로 바뀐 건 아닌지 로그 확인 |

**추측하지 않고 원문부터 눈으로 본다**는 순서가 핵심이다. 2번을 건너뛰면 없는 문제를 고치게 된다.

시나리오가 다양하고 방어 장치가 명확해서, 다음에 비슷한 걸 설계한다면 TDD가 잘 맞겠다고 느꼈다.

## 5. TTS 스피커 — MAX98357 I2S 앰프

### 왜 앰프 모듈이 필요한가

**ESP32-S3에는 내장 DAC이 없다.** 구형 ESP32에는 있었지만 S3에서 제거됐다. 그래서 스피커를 직접 물릴 수 없고 I2S 앰프가 필요하다. (부저처럼 PWM으로 삑 소리를 내는 건 되지만, 음성 재생은 안 된다.)

### ⭐ 전원과 그라운드 — 계속 헷갈렸던 부분 정리

| 구분 | 출처 | 이유 |
|---|---|---|
| **3.3V** | ESP32 보드 **내부** (USB 5V를 레귤레이터로 낮춘 것) | 마이크는 소비 전류가 작아 충분 |
| **5V** | **외부** 어댑터 | 앰프는 소리 낼 때 순간 전류가 큼 |
| **GND** | **하나로 묶음 (공통 그라운드)** | ↓ |

**핵심 원리**: 전압은 절대값이 아니라 **차이**다. "3.3V"는 *어떤 기준점보다* 3.3V 높다는 뜻이고, 그 기준점이 GND(0V)다. I2S 신호선은 "GND보다 몇 V 높은가"로 0/1을 판단하므로, **두 부품의 GND가 떨어져 있으면 각자의 0V가 달라 신호 판단 자체가 성립하지 않는다.**

> **규칙**: **+ (전원)는 부품별로 따로, − (그라운드)는 회로 전체가 반드시 하나로.**

※ 이 개념은 **Day 2 조도센서 때 "GND는 어디로 연결하든 상관없더라"** 고 관찰했던 것과 같은 원리다. 결국 하나로 이어지기만 하면 된다.

### 브라운아웃(Brown-out)

앰프를 3.3V에 같이 물리면:

1. 소리 낼 때 앰프가 순간적으로 큰 전류를 당김
2. ESP32 내부 레귤레이터가 못 버텨 3.3V가 순간 하강
3. ESP32의 전압 감시 회로가 오작동을 막으려 **스스로 리셋**
4. 결과 — 말할 때마다 보드가 꺼졌다 켜짐

전기가 **없는** 게 아니라 **부족해서** 생기는 문제라 블랙아웃이 아니라 브라운아웃이다.

### 배선 구성

브레드보드에 **전원 레일 2줄(3.3V / 5V) + 공통 GND 1줄**:

1. 외부 5V 어댑터 + → 5V 레일 (3.3V 레일과 **다른** 줄)
2. 어댑터 − → GND 레일
3. **ESP32 GND도 같은 GND 레일에** ← 공통 그라운드
4. MAX98357 VIN은 5V 레일, GND는 GND 레일

Day 2의 "3.3V/5V 레일 분리 + 공용 GND"가 그대로 재등장했다.

## 6. ⚠️ 막혔던 부분 ② — `SerialTimeoutException: Write timeout`

오늘 가장 오래 붙잡았던 문제다.

### 증상

```python
File "test.py", line 71, in play_to_esp32
    py_serial.write(b'P')
serial.serialutil.SerialTimeoutException: Write timeout
```

**단 1바이트를 보내는 데 실패했다.** 정상 상황에서는 일어날 수 없는 일이다.

### 진단 과정

처음엔 프로그램이 **아무 메시지 없이 그냥 멈췄다.** 원인을 볼 수 없어서 추측만 하게 되는 상황이었다. 그래서 먼저 **멈춤을 에러 메시지로 바꾸는 작업**부터 했다.

```python
# 수정 전
py_serial = serial.Serial(port=SERIAL_PORT, baudrate=BAUDRATE, timeout=1)

# 수정 후 — write_timeout 추가
py_serial = serial.Serial(port=SERIAL_PORT, baudrate=BAUDRATE,
                          timeout=1, write_timeout=2)
```

이 한 줄로 **무한 대기가 예외로 바뀌었고, 그제서야 "1바이트조차 못 보낸다"는 사실이 드러났다.**

### 원인

- pyserial의 Windows 백엔드는 오버랩드 I/O(Overlapped I/O)로 쓰기를 걸고, **요청 바이트 수와 실제 송신 바이트 수가 다르면** `SerialTimeoutException`을 던진다 — 즉 시간 초과가 아니라 **경로 단절**의 신호다.
- 1바이트 실패는 버퍼 포화로 설명되지 않는다 → **ESP32-S3 USB CDC 재열거(re-enumeration)** 로 포트 핸들은 열려 있지만 실제 엔드포인트가 죽은 상태로 추정.

### 조치

- 아두이노 시리얼 모니터 닫기
- **USB 재연결 + 보드 리셋**
- `serial.Serial()`에 `write_timeout` 명시, `rtscts=False` / `dsrdtr=False` / `xonxoff=False`로 흐름제어 강제 해제
- `reset_input_buffer()` 호출 위치를 `'P'` 전송 **이전**으로 이동
  (기존 코드는 전송 **후** 호출해서 **첫 ACK를 버릴 위험**이 있었다)

### 함께 발견한 별도 이슈 — 샘플레이트 불일치

`test.py`는 안내 문구에 16kHz라고 적혀 있는데 실제 코드는 `set_frame_rate(44100)`이었다.
이번엔 `.ino`의 I2S 스피커 설정도 44100이라 우연히 맞았지만, **프로젝트마다 값이 다르므로 항상 확인해야 한다.**

> **점검 규칙**: `.ino`의 `i2s_config.sample_rate` == 파이썬의 `set_frame_rate()`
> 다르면 목소리가 빠르거나 느리게 들린다.

### 💡 이 문제에서 배운 가장 큰 것

**무한 대기(`portMAX_DELAY`, timeout 없음)는 문제를 감춘다.**

```
ESP32:  "스피커 버퍼가 빌 때까지 기다린다"   ← 탈출구 없음
Python: "ESP32가 'K'를 보낼 때까지 기다린다" ← 탈출구 없음
```

양쪽 다 탈출구가 없으면 **교착(Deadlock)** 이 되고, 멈추기만 할 뿐 아무것도 알려주지 않는다.
**타임아웃은 성능을 위한 게 아니라 "원인을 볼 수 있게 만드는 장치"** 라는 걸 이번에 확실히 배웠다.

## 7. ⚠️ 막혔던 부분 ③ — `Could not open COM6, the port is busy`

**증상**: 컴파일은 성공(프로그램 저장공간 27%, 동적 메모리 7%)했는데 업로드 단계에서 `PermissionError(13, ...)` 발생.

**원인**: Windows PermissionError 코드 5는 "액세스 거부" — **다른 프로세스가 COM6을 점유**하고 있었다. 이전에 실행하던 파이썬 스크립트(`ai_assistant_emotion.py` 등)가 시리얼 포트를 닫지 않은 상태였다.

**해결**: 포트를 점유 중이던 파이썬 프로세스를 종료 → 업로드 정상 진행.

> **교훈**: ESP32 계열은 **파이썬 스크립트와 아두이노 IDE가 같은 COM 포트를 동시에 열 수 없다.**
> 업로드 전에는 항상 **시리얼 모니터와 파이썬 스크립트가 종료되어 있는지** 먼저 확인.

※ Day 3의 `Failed to open serial port`(웹페이지 vs 시리얼 모니터)와 **완전히 같은 원리**다. 대상만 브라우저에서 파이썬으로 바뀌었을 뿐이다. **포트는 배타적 자원이다.**

## 8. 아두이노 IDE 메모리 설정 — "메모리를 늘렸다"의 진위

업로드 문제를 해결하는 과정에서 Tools 메뉴의 값들을 만졌는데, 정확히 무엇이 바뀌는지 검증했다.

| 항목 | 실제로 늘리는 것 |
|---|---|
| **PSRAM** (OPI PSRAM) | **RAM** (동작 중 쓰는 메모리) — "메모리를 늘렸다"에 해당하는 진짜 항목 |
| **Partition Scheme** | **Flash** (프로그램 저장 공간) — RAM이 아니라 저장소 |
| **Flash Size** | 칩의 실제 플래시 용량을 IDE에 알려주는 값 |

**RAM과 Flash는 별개 개념**이라, 어떤 값을 바꿨는지에 따라 "메모리 늘렸다"는 설명의 정확도가 달라진다. 컴파일 결과에 나오는 "프로그램 저장공간 27%"는 Flash, "동적 메모리 7%"는 RAM을 가리킨다.

## 9. 대화 기억 시스템 (5교시)

`ai_assistant.py`를 대화 기억 확장 버전으로 발전시켰다.

| 계층 | 구현 | 목적 |
|---|---|---|
| **단기기억** | `conversation_history` 리스트에 발화 누적 | 직전 맥락 유지 |
| **트리밍** | `MAX_HISTORY_TURNS`(6)만 남기고 삭제<br>`del history[:-MAX_HISTORY_TURNS]` | 프롬프트가 무한정 길어지는 것 방지 |
| **장기기억** | `memory.json`에 매 턴 저장 | 프로그램을 껐다 켜도 `load_memory()`로 이어짐 |

### 동작 흐름

```
버튼(B) → 녹음(R) → STT
  → 히스토리에 발화 추가 + 트리밍
  → LLM 호출 → 응답도 히스토리에 추가
  → save_memory() → TTS → 재생(P)
```

**트리밍이 왜 필요한가** — LLM은 매 요청마다 히스토리 전체를 함께 보낸다. 자르지 않으면 대화가 길어질수록 요청이 무거워지고 비용도 늘어난다. **최근 6턴만** 유지하는 것이 그 대책이다.

## 10. 통합 펌웨어 — "듣고 있어요" 피드백 (6교시)

### 먼저, "통합 펌웨어"가 무슨 뜻인가

**펌웨어(Firmware)** 는 보드에 올리는 프로그램, 즉 `.ino` 파일이다. 지금까지는 교시마다 별도의 `.ino`를 만들어 그때그때 덮어썼다 — 마이크 테스트용, 스피커 테스트용, 버튼 테스트용이 따로 있었다.

**통합 펌웨어는 그 조각들을 하나의 `.ino`로 합친 것**이다. 보드에는 프로그램이 하나만 올라가므로, 마이크도 쓰고 스피커도 쓰고 버튼도 쓰려면 결국 하나로 합쳐야 한다.

**E2E(End-to-End)와는 층이 다르다.**

| 구분 | 범위 | 오늘의 경우 |
|---|---|---|
| **통합 펌웨어** | **보드 안**의 프로그램을 하나로 | 마이크 + 스피커 + 버튼 + LED + OLED를 한 `.ino`에 |
| **E2E 연결** | **시스템 전체**가 처음부터 끝까지 이어짐 | 버튼 → 마이크 → PC(STT·LLM·TTS) → 스피커 |

즉 **통합 펌웨어는 E2E 사슬 중 "보드가 맡은 구간"을 한 프로그램으로 묶은 것**이다. 보드는 사슬의 양 끝(입력·출력)을 담당하고, 가운데(STT·LLM·TTS)는 PC의 파이썬이 맡는다. 오늘 이 둘이 다 완성되면서 E2E가 처음으로 이어졌다.

### 무엇을 합쳤나

4교시(I2S 마이크·스피커 + 택트버튼) + 5교시(확인 피드백) + 6교시(OLED 표정)를 하나의 `.ino`로 합쳤다.

### 요구사항

버튼을 누른 **바로 그 순간** 소리(띠-띠)와 파란 LED로 "듣고 있어요"를 알려서, 사용자가 버튼이 눌렸는지 즉시 알 수 있게 한다. **새 부품 없이** 기존 스피커(MAX98357)와 보드 내장 RGB LED(네오픽셀)를 재사용한다.

### 구현 확인

`check_button()` 안에서 디바운스 처리 후 `Serial.write('B')`를 보내기 **직전**에 `play_confirm_feedback()`을 호출한다.

- 1400Hz 톤 2회 (60ms씩, 50ms 간격)
- 파란 LED 점멸

**호출 위치가 핵심이다.** `'B'`를 보낸 뒤에 피드백을 주면 PC 왕복 시간만큼 늦어진다. 누른 즉시 반응해야 "눌렸구나"를 알 수 있다.

| 증상 | 원인 | 해결 | 얻은 규칙 |
|---|---|---|---|
| `ESP32 응답 없음` | 포트 문제 **+ 마이크 불량** (2중) | 포트 재연결 + 마이크 교체 | 하나 고쳐도 증상이 남으면 **원인이 하나 더 있다** |
| `SerialTimeoutException` (1바이트 실패) | USB CDC 재열거로 엔드포인트 단절 | USB 재연결·보드 리셋, `write_timeout` 명시, 흐름제어 해제 | **타임아웃은 원인을 보이게 만드는 장치** |

| 샘플레이트 불일치 위험 | `.ino`와 `.py` 값이 따로 관리됨 | 두 값을 항상 대조 | 양쪽에 나뉜 설정은 **반드시 짝으로 점검** |

## 오늘 배운 것 한 줄 요약

- **디지털 센서는 변환이 아니라 약속(프로토콜)이 필요하다.** I2S의 선 3개 중 실제 데이터는 하나뿐이고, 나머지는 "언제·어느 쪽"을 알려주는 안내선이다.
- **대역폭이 유한하면 무엇을 버릴지 먼저 정해야 한다.** 오디오는 늦으면 가치가 없어 버려도 되고, 명령은 반드시 도달해야 한다. 이게 QoS다.
- **타임아웃은 성능이 아니라 관측을 위한 장치다.** 무한 대기는 문제를 감추고, 감춰진 문제는 고칠 수 없다.
- **전원은 나누고 그라운드는 묶는다.** 전압은 절대값이 아니라 기준점(GND)과의 차이이기 때문이다.
- **원인은 하나가 아닐 수 있다.** 이틀 연속으로 "부품 불량 + 설정 문제"가 겹친 케이스를 만났다.
- **LLM은 형식을 보장하지 않는다.** 그래서 강제·검증·재시도·폴백이 겹겹이 필요하다.
