## 1. 오늘의 설계 원리 — 역할 분리

오늘 배운 것 중 가장 중요한 개념은 **"LLM은 이름표만 고르고, 그 이름표를 하드웨어 명령으로 바꾸는 건 우리 몫"** 이라는 역할 분리다.

이 원리는 이미 앞 교시의 **표정(emotion)** 에서 한 번 배운 것이고, 오늘의 **몸짓(gesture)** 은 완전히 같은 패턴을 재사용한 것이다.

| | LLM이 고르는 것 | PC가 보내는 것 | 로봇이 하는 일 |
|---|---|---|---|
| **표정** (앞 교시) | `emotion = SAD` | `'E'` + JSON 한 줄 | OLED 눈이 슬퍼짐 |
| **몸짓** (오늘) | `gesture = 인사` | `'M'` + JSON 한 줄 | 내가 만든 인사 동작 재생 |

**LLM은 로봇팔 각도를 하나도 몰라도 된다.** "지금은 인사하는 상황"이라고 판단만 하면 되고, 그 이름표를 어떤 움직임으로 바꿀지는 우리가 만든 매핑 코드가 정한다.

이 분리 덕분에 얻는 실질적인 이득:

- 동작을 바꾸고 싶을 때 **LLM 프롬프트도, 펌웨어도 건드릴 필요가 없다.** 동작 파일만 새로 만들면 된다.
- 동작 데이터가 펌웨어 안에 없으므로, 보드는 **받은 대로 재생만** 한다.

## 2. 하드웨어: PCA9685 배선

새 GPIO는 하나도 쓰지 않았다. 앞 교시에 OLED를 붙인 I2C 두 선에 나란히 물리기만 하면 된다.

| PCA9685 핀 | 연결 대상 | 역할 |
|---|---|---|
| SDA | ESP32-S3 GPIO 8 (OLED와 공유) | I2C 데이터선 |
| SCL | ESP32-S3 GPIO 9 (OLED와 공유) | I2C 클럭선 |
| VCC | ESP32-S3 3.3V | 칩 동작 전원 (신호용) |
| GND | ESP32-S3 GND | 기준 전압 |
| **V+** | **서보 전용 외부 5V** | 모터 구동 전원 |

**같은 선에 붙여도 되는 이유**: I2C는 여러 장치가 나눠 쓰는 버스(bus)다. 장치마다 고유한 주소가 있어서 두 선만으로 여럿을 구분해 부른다 — OLED는 `0x3C`, PCA9685는 `0x40`.

### 전원은 따로, 접지는 함께

이 부분이 오늘 하드웨어에서 가장 중요한 규칙이다.

- **VCC (3.3V)**: PCA9685 칩이 "생각하는 데" 쓰는 전원. I2C 신호용이라 전류를 거의 안 쓴다.
- **V+ (외부 5V)**: 서보 모터를 실제로 돌리는 전원. 서보 4개가 동시에 움직이면 순간적으로 **1A 이상** 쓴다.

**V+를 ESP32의 5V/3.3V 핀에 꽂으면 안 된다.** 서보가 움직이는 순간 보드 전압이 훅 떨어지면서 ESP32가 리셋되고, COM 포트가 끊기며 실행 중이던 파이썬이 에러를 내며 멈춘다. "대화 도중에 갑자기 죽어요"의 대부분이 이 문제다.

**대신 GND는 반드시 하나로 묶어야 한다.** 외부 5V의 GND와 ESP32의 GND를 연결하지 않으면 두 회로의 기준이 달라져 I2C 신호를 못 알아듣는다.

## 3. 트러블슈팅: 로봇팔이 안 움직인 이유

실습 중 실제로 겪은 문제와 해결 과정을 그대로 기록해 둔다.

**증상**: 웹 도구에서 COM6 연결은 성공하고, 슬라이더를 움직이면 디버그 콘솔에 `송신 완료 ➔ {"s0":90,...}` 로그도 정상적으로 찍히는데, **서보가 전혀 움직이지 않았다.**

**처음 의심한 것**: GND 공통 접지 누락 (위에서 배운 대표적 실수)

**실제 원인**: **PCA9685의 신호용 VCC(3.3V) 핀 자체가 연결되어 있지 않았다.**

`V+`(외부 전원용)와 `VCC`(신호용)를 헷갈려서 VCC 연결을 빠뜨린 것이었다. 보드에 V+ 계열 단자가 여러 개 있는데, 보드끼리 전원을 공유하는 용도와 외부 전압을 받는 용도가 구분되어 있어서 더 헷갈렸다.

**왜 로그는 정상이었나 (중요한 교훈)**

디버그 콘솔의 "송신 완료"는 **PC ↔ ESP32 사이의 USB 시리얼 통신** 결과다. 이 경로는 PCA9685의 전원과 아무 상관이 없다. 진짜 문제는 그 다음 구간, 즉 **ESP32 → PCA9685 사이의 I2C 통신**에서 PCA9685가 전원을 못 받아 응답 자체를 못 하고 있던 것이었다.

> **일반화한 교훈**: 로그가 정상이라고 해서 그 뒤 구간까지 정상인 게 아니다.
> 로그는 "내가 보낸 것"만 증명하지, "상대가 받았는지"는 증명하지 않는다.
> 통신 경로를 구간별로 나눠서 어디까지 확인된 것인지 구분하는 습관이 필요하다.

VCC를 연결한 뒤 슬라이더 조작이 실제 서보 움직임으로 이어지는 것을 확인했다.

## 4. 동작 만들기 — 매크로 티칭

동작은 웹 도구(`동작만들기.html`)에서 **자세를 하나씩 기록해 이어 붙이는** 방식으로 만든다. 산업용 로봇의 티칭 팬던트와 같은 개념이다.

### 작업 흐름

1. 슬라이더로 4축(베이스 S0 / 위아래 S1 / 앞뒤 S2 / 그리퍼 S3)을 조작해 원하는 자세를 만든다
2. **[위치 기억(Teach)]** 을 눌러 그 자세를 목록 맨 뒤에 추가한다 (이동 시간 `spd`도 함께 저장)
3. 1~2를 반복해 자세를 쌓는다
4. **[재생 시작(Play)]** 으로 전체 시퀀스를 확인한다
5. 동작 이름과 설명을 적고 **[저장]** → `gestures/` 폴더에 `.json`으로 저장

### 저장되는 파일 형식

```json
{
  "name": "도리도리",
  "description": "좌우로 두 번 고개를 저으며 거절하는 동작",
  "steps": [
    { "s0": 65,  "s1": 90, "s2": 90, "s3": 90, "spd": 400 },
    { "s0": 115, "s1": 90, "s2": 90, "s3": 90, "spd": 400 },
    { "s0": 65,  "s1": 90, "s2": 90, "s3": 90, "spd": 400 },
    { "s0": 90,  "s1": 90, "s2": 90, "s3": 90, "spd": 500 }
  ]
}
```

- `name` — 동작 이름표
- `description` — **AI가 이 문장만 보고 동작을 고른다.** 언제 쓰는 동작인지 적어야 한다
- `steps` — 자세 목록. 각 자세는 4축 각도 + 그 자세까지 이동할 시간(ms)

### 서보에 "속도"를 명령할 수 없다는 문제

서보는 목표 각도만 받고, 얼마나 천천히 갈지는 명령할 수 없다. 그래서 펌웨어는 큰 이동을 **20ms 간격의 미세 이동 수십 개로 쪼개서** 보낸다. 이렇게 해야 전체 이동 시간을 우리가 제어할 수 있다.

```cpp
void moveSmooth(Pose target) {
  const int tick = 20;
  int steps = max(1, target.spd / tick);   // spd를 20ms 단위로 분할
  // ...
  for (int n = 1; n <= steps; n++) {
    for (int i = 0; i < 4; i++) {
      float a = start[i] + (target.s[i] - start[i]) * (float)n / steps;  // 선형 보간
      setServoAngle(i, (int)a);
    }
    delay(tick);
  }
  // ...
}
```

덕분에 자세를 촘촘히 넣지 않아도 된다. **핵심 자세 3~5개만 잡고 `spd`를 넉넉히 주면 중간 움직임은 보간으로 채워진다.**

### 알게 된 하드웨어 제약 — 손으로 옮겨 기록하기는 불가능

동작이 많아지자 "슬라이더 대신 팔을 손으로 잡고 원하는 자세로 옮긴 뒤, 그 각도만 기록하면 되지 않나?"(키네스테틱 티칭)를 시도해 보려 했으나, **지금 하드웨어로는 불가능**하다는 것을 확인했다.

- 일반 취미용 서보는 **출력 전용**이다. PCA9685는 PWM을 보내기만 하고, 서보가 지금 몇 도인지 **읽어오는 경로가 없다.**
- 전원이 켜진 상태에서 손으로 꺾으면 서보가 지시 각도를 유지하려 저항해 기어가 손상될 수 있다.
- 전원을 끄고 옮기면 팔은 움직이지만, 보드는 손으로 옮긴 실제 각도를 알 방법이 없다.

키네스테틱 티칭은 **각도 피드백을 읽을 수 있는 하드웨어**(포텐셔미터 피드백선을 뽑은 서보, 또는 스마트 서보)가 있어야 성립한다. 협동로봇에서 이 방식이 가능한 이유가 바로 관절마다 엔코더가 있기 때문이라는 걸 이 과정에서 이해했다.

## 5. 동작과 AI 연결하기 — 폴더가 곧 목록

`gesture_map.py`가 `gestures/` 폴더를 훑어서 **파일 이름을 그대로 이름표로** 만든다.

```python
def discover_gestures():
    """gestures/ 폴더의 .json 을 전부 찾아 이름표를 만든다."""
    for path in sorted(glob.glob(os.path.join(GESTURE_DIR, "*.json"))):
        label = os.path.splitext(os.path.basename(path))[0]   # 박수.json -> "박수"
        index[label] = path
```

### 폴더에서 자동으로 만들어지는 것

- 이름표 목록 (`gesture_labels()`)
- LLM에게 전달할 안내문 (`build_gesture_instruction()` — 각 파일의 `description`을 모아서 생성)
- 가드레일 허용 목록 (`ALLOWED_GESTURES`)

### 손댈 필요 없는 것

- 파이썬 코드 전체
- 펌웨어
- `SYSTEM_INSTRUCTION`

**동작을 추가하려면 `.json` 파일을 폴더에 넣고 파이썬을 다시 시작하면 끝이다.**

> `discover_gestures()`는 **모듈을 import할 때 딱 한 번만** 실행된다.
> 프로그램이 실행 중인 상태로 파일만 추가하면 그 세션에서는 인식되지 않는다. 반드시 재시작할 것.

확인은 로봇 없이도 가능하다:

```bash
python gesture_map.py
```

지금 인식된 동작 목록, 각 동작의 자세 개수, 설명 유무, 그리고 **LLM에게 실제로 전달될 프롬프트 문장**까지 출력해 준다.

### emotion과 gesture는 다른 축이다

헷갈리기 쉬운 부분이라 정리해 둔다.

| | **emotion** | **gesture** |
|---|---|---|
| 무엇을 바꾸나 | OLED 표정 + 효과음 | 로봇팔 동작 |
| 목록이 어디 있나 | 코드 안에 **고정** (`ALLOWED_EMOTIONS`) | `gestures/` **폴더**가 결정 |
| 늘리려면 | 코드를 고쳐야 함 | 파일만 추가 |
| 성격 | 닫힌 목록 | 열린 목록 |

표정은 종류가 몇 개 안 되니 코드에 박아둬도 되지만, 몸짓은 계속 늘어날 것이므로 파일 기반으로 열어둔 설계다.

### 가드레일

LLM이 목록에 없는 이름을 지어내도 프로그램이 죽지 않도록, 앞 교시에서 배운 것과 같은 방식의 안전장치를 건다.

```python
if data["gesture"] not in ALLOWED_GESTURES:
    data["gesture"] = "NONE"     # 모르는 값이면 움직이지 않음
```

## 6. 전체 데이터 흐름

```
[사람] 택트버튼 누르고 말하기
   |
   v
[ESP32] I2S 마이크로 녹음 -> 'R' 명령으로 PC에 오디오 전송
   |
   v
[PC] STT (Google Speech Recognition) -> 텍스트
   |
   v
[PC] memory.json의 최근 대화 + 새 발화를 합쳐 LLM에 질의
   |
   v
[LLM] 순수 JSON 한 덩어리로 응답
      {"emotion": "...", "gesture": "...", "reply": "..."}
   |
   v
[PC] 가드레일 검증 -> 허용 목록에 없으면 NEUTRAL / NONE으로 교체
   |
   +--> 'E' + JSON  --> [ESP32] OLED 표정 전환
   +--> 'P' + PCM   --> [ESP32] 감정 효과음 재생
   +--> 'M' + JSON  --> [ESP32] 로봇팔 동작 재생 --> 완료 시 'G' 반환
   |                    (gestures/<이름표>.json의 steps를 그대로 전송)
   |
   v
[PC] 그 사이 TTS 음성 합성 (edge-tts)
   |
   v
[PC] 'G' 수신 대기 -> 'P' + PCM으로 답변 음성 전송
   |
   v
[ESP32] I2S 스피커로 답변 재생
```

### 왜 `'G'` 신호를 기다리나 (동시성 문제)

보드는 한 번에 한 가지 일만 한다. 팔이 움직이는 2~3초 동안 그 일에만 매달려 있어서, 이때 오디오를 보내면 제때 받지 못해 **소리가 깨진다.**

그래서 동작이 끝나면 보드가 `'G'` 한 바이트를 보내 PC에게 알린다. 앞 교시 오디오 전송의 `'K'`(ACK) 핸드셰이크와 같은 패턴이다.

그런데 여기서 **놀고 기다리지 않는 최적화**가 들어간다:

```python
# 2) 몸짓 시작 — 완료를 기다리지 않고 바로 다음 줄로 (wait_done=False)
send_gesture_to_esp32(py_serial, ai_reply['gesture'], wait_done=False)

# 3) 팔이 움직이는 동안 PC는 음성을 합성한다 (1~2초)
await text_to_speech(ai_reply['reply'], mp3_path)

# 4) 이제 팔이 끝났는지 확인
if ai_reply['gesture'] != "NONE":
    wait_for_gesture_done(py_serial)

# 5) 답변 음성 재생
play_to_esp32(mp3_path)
```

팔이 움직이는 시간과 TTS 합성 시간이 **겹쳐서 사라진다.** 하드웨어의 제약(한 번에 한 가지)을 인정하면서도, 서로 다른 장치가 각자 할 일을 병렬로 하게 만든 설계다.

## 7. 추가 미션: CV 드로잉 봇 (미완)

정규 실습 외 추가 미션으로 **카메라로 손동작을 인식해 그림을 그리는 드로잉 봇**이 주어졌다.

OpenCV.js 기초(이미지 로드, 픽셀값 확인, 도형 그리기, 그레이스케일 변환)까지는 따라갔으나, **손동작 인식과 로봇팔 제어를 연결하는 단계까지는 완성하지 못했다.** 결과물이 없어 여기서는 시도했다는 사실만 남겨 둔다.

다뤄본 OpenCV.js 개념:

| 단계 | 내용 | 핵심 API |
|---|---|---|
| 1 | `<img>` 이미지를 Mat(행렬) 객체로 가져와 `<canvas>`에 출력 | `cv.imread`, `cv.imshow` |
| 2 | 캔버스 위 마우스 좌표의 픽셀 RGB 값 실시간 확인 | — |
| 3 | 빈 Mat에 선·사각형·원 그리기 | `cv.line`, `cv.rectangle`, `cv.circle` |
| 4 | RGB 3채널 → 밝기 1채널로 압축 | `cv.cvtColor` |

**그레이스케일을 전처리로 쓰는 이유**: 객체의 외곽선·코너 같은 기하학적 형태를 파악하는 필터 연산에서 색상 3채널은 데이터 용량을 3배로 늘려 연산량만 가중시킨다. 형태 정보가 손상되지 않는 범위에서 1채널로 줄여 리소스를 아끼는 것.

**남은 과제**: 손 랜드마크 추출 → 좌표를 로봇팔 각도로 변환(역기구학) → 궤적 생성. 이 파이프라인을 이어붙이는 것이 다음 목표다.

## 8. 배운 것 정리

### 설계

- **역할 분리**: LLM은 이름표만 고르고, 하드웨어 명령 변환은 코드가 담당한다. 이 경계 덕분에 동작을 바꿔도 프롬프트와 펌웨어를 건드리지 않는다.
- **데이터와 코드의 분리**: 동작 데이터를 펌웨어에서 빼내 파일로 옮기니, 동작을 만들 때와 AI로 쓸 때 펌웨어를 바꿔 끼울 필요가 없어졌다. 보드는 받은 대로 재생만 한다.
- **닫힌 목록 vs 열린 목록**: 개수가 고정된 것(표정)은 코드에, 계속 늘어날 것(몸짓)은 파일 기반으로. 확장 빈도가 저장 위치를 결정한다.
- **가드레일**: LLM 출력은 신뢰하지 않고 허용 목록으로 검증한다. 모르는 값이 와도 프로그램은 죽지 않고 조용히 넘어간다.

### 하드웨어

- **전원은 따로, 접지는 함께**: 신호용 전원(VCC)과 구동용 전원(V+)은 분리하되 GND는 공통으로 묶는다.
- **I2C는 버스다**: 주소가 다르면(0x3C, 0x40) 같은 두 선에 여러 장치를 붙일 수 있다.
- **서보는 출력 전용**: 각도를 보낼 수는 있어도 읽어올 수는 없다. 이 제약이 무엇을 가능하게 하고 무엇을 막는지 이해했다.
- **속도 제어는 보간으로**: 서보에 속도를 명령할 수 없으므로, 큰 이동을 미세 이동으로 쪼개 시간을 제어한다.

### 디버깅

- **로그는 구간을 증명하지 않는다**: "송신 완료"는 내가 보낸 것만 증명한다. 통신 경로를 구간별로 나눠 어디까지 확인된 것인지 구분해야 한다.
- **가설의 순서**: 흔한 실수(GND 누락)부터 의심한 것은 합리적이었지만, 실제 원인은 더 앞 단계(VCC 미연결)였다. 값싼 확인부터 순서대로 좁혀가는 방식은 유지하되, 한 가설에 갇히지 않아야 한다.

### 동시성

- 보드는 한 번에 한 가지 일만 한다 → 완료 신호(`'G'`) 핸드셰이크로 순서를 보장.
- 다만 기다리는 시간을 놀리지 않고 PC 쪽 작업(TTS 합성)과 겹쳐 실제 체감 지연을 없앴다.

```
06_robot_gesture/
├── 동작만들기.html                    # 매크로 티칭 웹 도구 (Web Serial)
├── gestures/                          # 동작 파일 폴더 (= AI가 고를 수 있는 목록)
│   ├── 인사.json
│   ├── 도리도리.json
│   └── 머리아파.json
├── step1_gesture_map/
│   └── gesture_map.py                 # 폴더 스캔 → 이름표 매핑 → 'M' 전송
├── step2_.../
│   └── ai_assistant_gesture.py        # STT + LLM + TTS + 표정 + 몸짓 통합 루프
└── esp32_voice_agent_gesture/
    └── esp32_voice_agent_gesture.ino  # 통합 펌웨어 (한 번만 업로드)
```

### 시리얼 명령 규격

| 명령 | 방향 | 내용 |
|---|---|---|
| `'B'` | ESP32 → PC | 택트버튼 눌림 알림 |
| `'R'` | PC → ESP32 | 녹음 요청 (5초 분량 PCM 회신) |
| `'P'` | PC → ESP32 | 오디오 재생 (길이 4바이트 + PCM, `'K'` ACK로 흐름 제어) |
| `'E'` | PC → ESP32 | 표정 전환 (`E{"emotion":"HAPPY"}\n`) |
| `'M'` | PC → ESP32 | 몸짓 재생 (`M{"steps":[...]}\n`, 완료 시 `'G'` 회신) |
| `'{'` | 웹 → ESP32 | 매크로 티칭 (teach / set / play / stop / clear / home) |

한 바이트 명령과 JSON 한 줄의 조합이라는 동일한 패턴이 전 구간에서 반복된다. `'{'`로 시작하는 매크로 명령은 한 바이트 명령들과 겹치지 않아 자연스럽게 구분된다.
