## 0. 오늘 만든 것의 전체 구조

오늘의 목표는 **폰에서 버튼을 누르면 내 PC가 실제로 반응하는** 시스템이다. 전체가 3계층으로 나뉜다.

| 계층 | 역할 | 구현 도구 |
|---|---|---|
| ① 폰 화면 | 버튼을 배치한 웹페이지. 누르면 **신호만** 보낸다 (동작 자체는 안 함) | HTML + JS (`WebSocket`) |
| ② 연결 통로 | 폰과 PC를 잇는 **웹소켓**. 전화처럼 연결을 계속 열어둔다 | `ws://` 프로토콜 |
| ③ PC 파이썬 | 신호를 받아 CLI 명령·키보드 입력으로 변환해 OS에 실행 | Python (`websockets`, `subprocess`, `pyautogui`) |

핵심 통찰: **폰 화면은 "명령을 실행"하는 게 아니라 "신호를 보낼" 뿐이다.** 실제 실행은 전부 ③ PC 파이썬이 한다.

## 1. 개발 환경 — conda 가상환경으로 파이썬 버전 맞추기

### 왜 시스템 파이썬에 덮어쓰지 않았나

강사님은 "그냥 파이썬을 덮어 깔라"고 안내했지만, 가상환경 분리를 택했다. 이유:

- 시스템 파이썬을 덮어쓰면 **되돌리기 어렵고**, 다른 프로젝트가 특정 버전에 의존했다면 조용히 깨진다.
- 버전 충돌은 결국 온다 — 처음부터 분리해두면 그 문제 자체가 안 생긴다.
- 파이썬 공식도 PEP 668 이후 시스템 파이썬 직접 설치를 막는 추세.

부트캠프에서 "덮어쓰기"를 권한 건 **가르치기 쉬워서**(전원이 같은 상태라 디버깅이 빠름)이지, 최선의 실무 습관이라서가 아니다.

### conda vs venv

| | conda | venv |
|---|---|---|
| 버전 관리 | `conda create -n 이름 python=3.12`로 특정 버전 자체를 새로 깖 | 이미 설치된 버전 위에서만 격리 |
| 데이터/AI 계열 | CUDA·PyTorch 등 비-파이썬 바이너리까지 관리 (로보틱스/비전에 유리) | pip 그대로, 특별한 이점 없음 |

로보틱스·비전 패키지(`lerobot_env`, `DepthAnything` 등)를 쓰는 환경이라 conda가 적합했다.

### 겪은 트러블슈팅 — 채널 문제

```powershell
conda create -n monolis python=3.12.10 -y
# → PackagesNotFoundError: python=3.12.10
```

**원인**: 기본 `defaults` 채널에는 3.12.10 패치 버전 빌드가 없다. `defaults`는 모든 패치 버전을 다 올려두지 않는다.

**해결**: `conda-forge` 채널을 명시하면 된다. conda-forge는 훨씬 많은 버전을 제공하는 커뮤니티 채널.

```powershell
conda create -n monolis -c conda-forge python=3.12.10 -y
conda activate monolis
python --version   # → Python 3.12.10
```

> 배운 것: "아나콘다에 3.12.10이 없다"가 아니라 **"defaults 채널엔 없고 conda-forge 채널엔 있다"**가 정확한 표현.
> 같은 conda 생태계 안에서도 채널마다 올라온 패키지가 다르다.
> 설치 후 `conda list -n monolis python`의 맨 오른쪽 열에서 어느 채널에서 왔는지 확인할 수 있다.

### 참고 — 요즘은 conda 말고 uv?

Rust로 만든 `uv`(pip·virtualenv·pyenv 통합, 압도적 속도)가 뜨고 있지만, **지금은 안 옮겨도 된다.** uv/pip는 PyPI 순수 파이썬 패키지만 다루고, conda는 CUDA·PyTorch 같은 시스템 라이브러리까지 관리한다. GPU 패키지를 쓰는 지금 환경엔 conda가 안정적. 참고로 지금 쓰는 `miniconda3 + -c conda-forge` 조합은 최근 트렌드인 "Miniforge + conda-forge 기본"과 사실상 같은 효과다.

## 2. 웹소켓 — 실시간 양방향 통신

### HTTP(REST) vs 웹소켓

| | REST (HTTP) | 웹소켓 |
|---|---|---|
| 연결 | 요청마다 새로 연결 (핸드셰이크 매번) | 최초 1번만 연결하고 계속 유지 |
| 방향 | 클라이언트가 물어봐야만 서버가 답함 | 서버가 **먼저** 말 걸 수 있음 (양방향) |
| 프로토콜 | `http://` / `https://` | `ws://` / `wss://` |

핵심 차이는 속도보다 **"누가 먼저 말을 거느냐"**다. "PC 상태를 폰에 실시간으로 계속 띄우기" 같은 건 REST면 폰이 1초마다 계속 물어봐야 하지만(비효율), 웹소켓은 PC가 상태 바뀔 때 알아서 밀어줄 수 있다.

### 브라우저는 왜 PC를 직접 제어하지 못하나 — 샌드박스

웹페이지의 JS는 **격리된 브라우저 내부 상자(샌드박스) 안에서만** 실행된다. 임의 웹사이트가 접속자의 PC 파일·프로그램을 무단 실행하는 걸 근본적으로 차단하는 **필수 보안 장치**다. 오류가 아니라 의도된 설계.

**그럼 Node.js는 BE에서 되잖아?** — 모순 아니다. 권한을 가르는 건 "JS인지 아닌지"가 아니라 **"브라우저 탭 안에서 도는지, OS 위에서 독립 프로세스로 도는지"**다.

| | 실행 위치 | PC 접근 |
|---|---|---|
| 웹페이지 `<script>` (프론트 JS) | 브라우저 샌드박스 안 | ❌ 불가 |
| Node.js | OS 위 독립 프로그램 | ✅ 가능 |

Node.js는 "감옥을 탈출한 JS"가 아니라 **애초에 브라우저 감옥에 들어간 적 없는 별개 실행기**다. 오늘 ③ PC 파이썬 자리는 파이썬 대신 Node.js로 짰어도 똑같이 됐다.

### echo 서버 실습 — 코드 해부

**서버 (`02_1_echo_server.py`)**

```python
import asyncio, websockets

async def handler(websocket):
    print("폰이 연결되었습니다!")
    async for message in websocket:      # 메시지 올 때마다 루프 1회
        await websocket.send(message[::-1])  # 거꾸로 뒤집어 되돌려보냄

async def main():
    async with websockets.serve(handler, "0.0.0.0", 3000):
        print("서버 시작 (Port: 3000)")
        await asyncio.Future()           # 서버가 안 꺼지게 무한 대기

asyncio.run(main())
```

- `handler`는 폰이 접속할 때마다 자동 실행되는 **서비스 창구**. `websocket`은 "지금 이 폰과 연결된 통로" 그 자체.
- `async for message in websocket:` — REST처럼 한 번 받고 끝이 아니라, **폰이 메시지 보낼 때마다 루프가 계속 돌며** 하나씩 받는다. (연결 유지의 핵심)
- `message[::-1]` — 받은 걸 그대로 안 보내고 거꾸로 뒤집어서 보낸다. "정말 서버가 응답한 건지, 내가 친 글자가 남은 건지" 구분하기 위한 검증용.

**클라이언트 (`02_2_echo_test.html`)**

```javascript
const socket = new WebSocket("ws://192.168.0.160:3000");
socket.addEventListener('open',    () => echo.textContent = "✅ 연결 성공!");
socket.addEventListener('message', (e) => echo.textContent = e.data);
```

- `new WebSocket(...)` 이 줄이 서버 `handler`를 실행시키는 방아쇠. 이 줄 실행 순간 서버에 "폰이 연결되었습니다!"가 찍힌다.
- `'open'` — 연결 성공 순간 딱 1번. `'message'` — 서버가 뭔가 보낼 때마다.
- 클라이언트의 `id="msg"`(입력창 이름표)와 서버의 `message`(받은 문자열 값)는 **이름이 비슷할 뿐 아무 관계 없다.** 둘을 연결하는 건 이름이 아니라 웹소켓 통신 자체.

### "덮어쓰기" 실험 — 대입(`=`) vs 누적(`+=`)

선택 미션으로 서버가 두 번 `send`하게 만들었더니(`message[::-1]`와 `"라고 하셨군요!"`), 화면엔 마지막 것만 보였다.

**원인은 덮어쓰기.** 클라이언트가 `echo.textContent = e.data`로 **대입 연산자(`=`)**를 쓰기 때문. 메시지가 올 때마다 이전 내용을 지우고 새 값으로 갈아치운다. 서버가 2번 보냈지만, 사람 눈엔 지연이 없어 첫 번째는 인식할 새 없이 두 번째로 덮인 것.

**개발자도구로 직접 검증** (F12 → Network → WS → 그 요청 클릭 → Messages 탭):
- `↑안녕` (내가 보낸 것, Length 2)
- `↓녕안` (message[::-1], Length 2)
- `↓안녕 라고 하셨군요!` (Length 11)

`↓`가 2번 찍혀 있고 Length가 각각 다른 것 = 두 개의 독립 메시지가 도착했다는 증거. "덮어쓰기" 가설이 눈으로 완전히 증명됨.

### `async for message in websocket:`의 `message`는?

이건 라이브러리가 정한 고정 이름이 아니라 **그 줄에서 즉석으로 지은 지역변수**. 일반 `for x in [1,2,3]:`의 `x`처럼, `msg`·`data`·아무개로 바꿔도 동작 동일. `websocket`·`handler`처럼 함수 매개변수 자리에 있는 이름은 못 바꾸지만, 루프 변수는 자유롭게 바꿀 수 있다.

## 3. 네트워크 실측 — IP · 포트 · TCP

### 포트는 프로그램마다 하나씩

PC 안에 두 서버가 동시에 떠 있었다.

| 프로그램 | 포트 | 역할 |
|---|---|---|
| Five Server (VS Code 확장) | 5500 | HTML·CSS·JS 파일 전달 (HTTP) |
| `03_2_simple_server.py` | 3000 | 웹소켓 신호 처리 |

두 프로세스는 서로 모르는 남남. 같은 포트를 두 프로세스가 못 쓴다(아파트 한 호실에 두 세대 불가). 그래서 5500과 안 겹치게 3000을 쓴 것. 만약 5500으로 열려 했다면 `address already in use` 에러로 시작조차 못 했을 것이다.

**포트를 "가지는" 순간**은 `websockets.serve(handler, "0.0.0.0", 3000)`이 실행될 때(OS에 bind). `await asyncio.Future()`는 포트 유지가 아니라 **프로그램이 안 죽게 붙잡는 것**.

- `"0.0.0.0"` = **누구한테서** 오든 다 받음 (허용 범위)
- `3000` = **어느 문(포트)으로** 받을지

즉 "3000번을 허용한다" = "3000번 포트를 열어 대기 중이다"와 같은 말.

### netstat으로 눈으로 확인

```powershell
netstat -ano | findstr 3000
```

- `netstat` = 지금 이 순간의 모든 네트워크 연결 목록 (로그가 아니라 실시간 스냅샷)
- `-ano` = `-a`(대기 중 포함) `-n`(숫자로) `-o`(PID 표시)
- `|` = 왼쪽 출력을 오른쪽 입력으로 넘김 (파이프)
- `findstr 3000` = "3000" 들어간 줄만 필터

접속 전:
```
TCP    0.0.0.0:3000    0.0.0.0:0    LISTENING    9536
```
- `TCP` = 웹소켓은 TCP 위에서 돈다는 게 실제로 찍힌 것
- `LISTENING` = "문 열고 대기 중" (아직 아무도 접속 안 함)
- `9536` = 이 포트를 점유한 프로세스 번호(PID)

접속 후(브라우저로 접속하자 줄이 3개로):
```
TCP  0.0.0.0:3000            0.0.0.0:0            LISTENING   9536   ← 새 손님 받는 문
TCP  192.168.0.160:3000      192.168.0.160:65321 ESTABLISHED 9536   ← 서버가 본 이 연결
TCP  192.168.0.160:65321     192.168.0.160:3000  ESTABLISHED 20872  ← 클라이언트가 본 같은 연결
```

**배운 것들**:
- `LISTENING`(대기) → `ESTABLISHED`(연결됨)로 상태가 바뀐다.
- `LISTENING` 줄은 그대로 유지되고, 접속자가 늘 때마다 `ESTABLISHED`가 추가된다 (문 하나로 여러 명 드나듦).
- 같은 PC에서 테스트해서 `ESTABLISHED`가 2줄 — **하나의 통화를 서버(9536)와 클라이언트(20872=Chrome)가 각자 자기 관점에서 기록**한 것. 입장만 다르지 같은 연결.
- `0.0.0.0`(코드의 와일드카드="누구나 환영")이 실제 연결 시 `192.168.0.160`(진짜 IP)으로 구체화된다.
- 이 "양쪽 대칭 기록"은 웹소켓 특징이 아니라 **TCP 전체의 성질**. 웹소켓은 연결을 오래 유지해서 우리가 관찰할 여유를 준 것뿐. (REST도 순간적으로 똑같이 생기지만 금방 사라짐)

### IP는 왜 자꾸 바뀌나 — DHCP

장소를 옮겨 와이파이가 바뀌자 연결이 끊겼다. 라우터마다 **DHCP**로 접속 기기에 IP를 자동 배정하는데, 다른 라우터(다른 장소)로 옮기면 관리 주소 범위 자체가 달라 IP가 통째로 바뀐다(이사 가면 우편번호 바뀌는 것과 같음).

```powershell
ipconfig   # 무선 LAN 어댑터 Wi-Fi → IPv4 주소 확인
```
확인한 새 IP로 클라이언트 HTML의 `new WebSocket("ws://새IP:3000")`만 바꾸면 됨. 서버는 `0.0.0.0`이라 안 건드려도 된다.

### wss는 왜 주소창에서 못 봤나

주소창의 `http`/`https`는 **페이지 자체**를 받아온 프로토콜. 웹소켓은 페이지 로드 뒤 JS가 여는 **별도 연결**이라 주소창엔 안 뜬다(`fetch`도 마찬가지). 개발자도구 Network 탭에서만 `ws://`/`wss://` 확인 가능.

**중요 규칙**: 페이지가 `https`면 그 안에서 `ws://`(평문)는 브라우저가 차단(Mixed Content). 이땐 `wss://`만 허용. 지금은 `http://127.0.0.1:5500`이라 `ws://`가 허용된 것. 나중에 `https`로 배포하면 `wss://`가 필수가 된다.

### TCP vs UDP — HTTP·WS와의 관계

"REST=TCP, 웹소켓=UDP" 아니다. **HTTP도 웹소켓도 둘 다 TCP 위에서 돈다.** 이들은 같은 층이 아니라 위아래 관계:

```
[애플리케이션 계층]  HTTP(REST)      WebSocket
                          \            /
[전송 계층]                 TCP            UDP  ← TCP와 같은 층의 다른 선택지
                             |
[네트워크 계층]              IP
```

- TCP = 순서 보장·유실 시 재전송 (신뢰성). 웹소켓도 이 신뢰성을 물려받아 "명령이 씹히면 안 되는" 상황에 적합.
- UDP = 신뢰성 포기 대신 빠름. DNS·실시간 스트리밍·게임에 쓰임. HTTP/WS와는 무관한 제3의 길.

## 4. 비동기 프로그래밍 (async / await)

### 동기 vs 비동기 — 커피 실습

```python
# 동기: 한 잔 끝나야 다음 잔 → 총 12초
make_coffee("아메리카노", 7); make_coffee("카페라떼", 4); make_coffee("자몽주스", 1)

# 비동기: 세 잔 동시 시작 → 총 7초 (가장 오래 걸리는 잔 기준)
await asyncio.gather(
    make_coffee("아메리카노", 7),
    make_coffee("카페라떼", 4),
    make_coffee("자몽주스", 1),
)
```

**결정적 차이**: 동기든 비동기든 "위에서 아래로 순서대로 진행"은 같다. 진짜 다른 건 **"대기하는 동안 그 시간을 다른 작업에게 양보하느냐"**.

- `time.sleep(1)` — 양보 못 함. 그 자리에서 CPU 붙잡고 멈춤 (동기, 12초의 원인).
- `await asyncio.sleep(1)` — "나 쉬는 동안 딴 사람 써도 돼"라고 **명시적으로 제어권 반납**. 이 반납이 있어야 그 시간에 다른 코루틴이 실행됨.

### 동시성(Concurrency) ≠ 병렬성(Parallelism)

이건 병렬이 아니라 **동시성**이다.

| | 동시성 (asyncio) | 병렬성 |
|---|---|---|
| 실행 주체 | 바리스타 **1명**(단일 스레드) | 바리스타 여러 명(멀티코어/스레드) |
| 방식 | 대기 시간에 왔다 갔다 하며 낭비 없이 처리 | 물리적으로 진짜 동시에 실행 |
| 필요 조건 | 코드 몇 줄(`async`/`await`) | 하드웨어·프로세스 분리 |

**핵심 통찰**: 원래 "동시에 여러 일"을 하려면 서버를 나누거나 스레드를 여럿 띄워야 한다고 생각하기 쉽지만, **asyncio는 나누지 않고도 나눈 것과 같은 효율을 내는 제3의 길**이다. "기다리는 시간(I/O 대기)"이 있는 작업이라면 그 틈새를 서로 빌려 쓰며 하나의 프로세스 안에서 여러 일을 번갈아 처리한다. 웹소켓·채팅·실시간 대시보드 서버에서 asyncio가 많이 쓰이는 이유.

### 서버에 적용 — 명령 수신 + 상태 전송 동시에

`async`를 붙였다고 자동으로 여러 일을 하는 게 아니다. `handler`엔 `async for` 루프 하나뿐이라 "폰 명령 기다리기" 한 가지만 반복한다. "CPU 상태 1초마다 보내기"를 추가하려면 **별도 코루틴을 하나 더 만들어 동시에 등록**해야 한다.

```python
async def send_system_stats(websocket):
    try:
        while True:
            cpu = psutil.cpu_percent()
            memory = psutil.virtual_memory().percent
            await websocket.send(json.dumps({"cpu": cpu, "memory": memory}))
            await asyncio.sleep(1)   # 1초 대기 중 제어권 양보
    except websockets.exceptions.ConnectionClosed:
        pass

async def handler(websocket):
    print("클라이언트가 무선 연결되었습니다!")
    monitor_task = asyncio.create_task(send_system_stats(websocket))  # 백그라운드 등록
    try:
        async for message in websocket:
            ...  # 기존 if/elif 분기
    finally:
        monitor_task.cancel()   # 연결 끊기면 반드시 정리
```

**핵심은 `asyncio.create_task(...)`** — `send_status`를 독립 작업으로 등록해 명령 수신 루프와 동시에 돈다. `send_status`가 `sleep(1)`로 대기 중이면 그 틈에 `handler`가 명령 처리, 반대도 마찬가지.

- 만약 `create_task` 없이 `await send_status(...)`로 순서대로 불렀다면? `while True`가 영원히 안 끝나 `async for`에 도달을 못 해 **폰 명령을 영영 못 받는다**(폰 화면 숫자가 얼어붙음).

### `gather` vs `create_task`

| | 언제 |
|---|---|
| `asyncio.gather(A, B, C)` | 끝이 있는 작업들을 한꺼번에 (커피 3잔) |
| `asyncio.create_task(A)` | 끝나지 않고 계속 도는 작업을 곁다리로 (`send_status`의 `while True`) |

### `try/finally`가 필요한 이유 — 좀비 태스크 방지

`monitor_task`는 `handler`와 독립적으로 도는 작업이라, `handler`가 끝나도 자동으로 안 꺼진다. 정리 안 하면 이미 끊긴 연결에 계속 `send`를 시도하는 **좀비 태스크**로 남아 리소스를 누수한다. `finally`는 루프가 정상 종료되든 에러로 중단되든 **무조건 실행**되는 자리라, "어떻게 끊기든 반드시 정리"를 보장한다. 두 안전장치가 서로 다른 타이밍을 담당:
- `handler`의 `finally` → 루프가 정상 종료됐을 때
- `send_system_stats`의 `except` → 그 전에 먼저 전송이 실패했을 때

## 5. PC 제어 — subprocess · pyautogui

### CLI vs GUI, 그리고 AI가 CLI를 쓰는 이유

- GUI: 아이콘을 마우스로 클릭 — AI 입장에선 느리고 오류 잦음
- CLI: 텍스트 명령 한 줄로 즉시·정확히 실행 — 실행 결과·오류도 텍스트라 AI가 바로 해결 가능

명령어엔 **인자(argument)**로 세부 주문이 가능하다: `start chrome https://google.com/search?q=피지컬AI`

### subprocess — 정해진 프로그램 실행

```python
elif message == "open_chrome":
    subprocess.Popen("start chrome https://www.google.com/search?q=파이썬+자동화", shell=True)
```

**`Popen` vs `run`** — 이게 비동기 원칙과 직결된다:

| | 동작 | 서버에 쓰면 |
|---|---|---|
| `subprocess.run(...)` | 프로그램 끝날 때까지 기다림(blocking) | 메모장 안 끄면 서버 전체가 얼어붙음(먹통) |
| `subprocess.Popen(...)` | 띄워놓고 바로 다음 줄로(non-blocking) | 서버는 즉시 다음 신호 받을 준비 |

`Popen`을 쓴 이유 = "비동기 서버는 절대 멈추면 안 된다"는 원칙을 지키기 위해. (`Popen`은 원래 안 기다리는 함수라 `await` 없이도 서버가 안 멈춤)

### pyautogui — 마우스·키보드 자체를 조작 (매크로의 원리)

`subprocess`가 "정해진 프로그램 실행"이라면 `pyautogui`는 한 단계 더 나아가 **마우스·키보드를 프로그램이 대신 조작**한다.

```python
pyautogui.moveTo(500, 500, duration=1)   # 절대 좌표로 1초에 걸쳐 이동
pyautogui.moveRel(200, 0, duration=0.5)  # 현재 위치 기준 상대 이동
pyautogui.write("Hello", interval=0.1)   # 한 글자씩 실제 타이핑
pyautogui.press("volumeup")              # 볼륨 키 입력
pyautogui.size()                         # 모니터 해상도
```

게임 매크로·반복 업무 자동화가 원리상 다 이것. 오늘 3계층 구조와 합치면 "폰 버튼 → PC가 매크로 실행"도 가능하다.

### 한글 입력 문제 — pyperclip + Ctrl+V

```python
if message.startswith("pc_type:"):
    text = message.replace("pc_type:", "", 1)  # 명령 이름 떼고 순수 텍스트만
    pyperclip.copy(text)          # 클립보드에 복사
    pyautogui.hotkey("ctrl", "v")  # 붙여넣기 (한글·이모지도 정상)
```

`pyautogui.write()`는 키를 한 글자씩 누르는 흉내라 **영어(키=글자)는 되지만 한글(자음+모음 조합)은 안 된다.** 그래서 "클립보드에 복사 → 붙여넣기 키만 누름"으로 우회. 붙여넣기는 완성된 텍스트를 통째로 넣어 한글·이모지 다 됨.

- `startswith("pc_type:")` — `==`(완전 일치)와 달리 **"명령 종류(Prefix) + 가변 데이터(Payload)"** 구조를 파싱하는 표준. 매번 다른 문장을 실어 보내야 하니 필요.
- `replace("pc_type:", "", 1)`의 세 번째 인자 `1` — 최초 1회만 치환. 사용자 입력에 우연히 `pc_type:`이 또 있어도 그것까지 지우는 사고 방지.

### 파일 경로 — 하드코딩하지 않는 이유

```python
SAVE_DIR = os.path.dirname(os.path.abspath(__file__))
pyautogui.screenshot(os.path.join(SAVE_DIR, "screenshot.png"))
```

- `__file__` = 실행 중인 이 .py 파일 자신의 경로
- `os.path.abspath(...)` = 무조건 절대경로로 (실행 위치에 안 흔들리게)
- `os.path.dirname(...)` = 파일명 떼고 폴더 경로만
- `os.path.join(...)` = OS별 경로 구분자(`\` vs `/`) 자동 처리

**왜 이렇게까지?** 그냥 `"screenshot.png"`(상대경로)로 하면 "터미널을 어디서 열었는지(CWD)" 기준으로 저장돼 엉뚱한 곳에 떨어진다. `SAVE_DIR`을 쓰면 어디서 실행하든 항상 "코드 파일 옆"에 저장된다.

> 배운 것: 이건 **배포·협업을 위한 규칙**이다. 팀원마다 경로가 다르고 배포 서버 경로도 다른데, 하드코딩하면 다른 컴퓨터에선 그 경로가 없어 바로 에러. "지금 내 컴퓨터, 지금 이 상황"에만 맞는 코드가 아니라 **"누가 언제 어디서 실행해도 똑같이 동작하는" 코드**를 짜는 게 실무 기본기. 서버 IP를 `0.0.0.0`으로 연 것, 화이트리스트, 비동기 처리 모두 같은 철학이다.

### 트러블슈팅 — pyautogui 스크린샷 에러

```
pyautogui.PyAutoGUIException: PyAutoGUI was unable to import pyscreeze.
(This is likely because you're running a version of Python that Pillow doesn't support currently.)
```

`pyautogui.screenshot()`는 내부적으로 `pyscreeze` → `Pillow`(이미지 처리)에 의존. 이 연결고리가 끊겨서 난 에러. `pip install --upgrade pyautogui`를 해도 안 됐는데, 설치 로그를 보니 **Pillow가 목록에 없다** — Pillow는 pyautogui의 직접 의존성이 아니라 pyscreeze의 의존성이라 pip가 깊이 확인 안 하고 넘어감.

**진짜 원인 확인법**:
```powershell
pip show pillow           # 설치 여부·버전 확인
python -c "import pyscreeze"   # pyautogui 거치지 않고 직접 불러 진짜 에러 보기
```
`pip install Pillow`로 해결. (참고: 이 에러 메시지는 실제로는 다른 import 실패를 다 이 문구로 퉁쳐 보여주는 경우가 많음)

## 6. 보안 — 직접 뚫어보며 배운 것

### 화이트리스트 — 받은 문자열을 그대로 실행하지 않기

```python
# ❌ 위험 — 클라이언트가 보낸 걸 그대로 실행
subprocess.run(received_message)

# ✅ 화이트리스트 — 정해진 "이름"만 받고, 실제 명령은 서버가 가짐
if message == "open_notepad":
    subprocess.Popen("notepad.exe")
```

클라이언트는 "실제 실행될 명령어"를 못 보내고, 서버가 미리 정한 **이름표**만 골라 보낼 수 있다. 목록에 없으면 무조건 거부.

### 직접 뚫어본 취약점 — 인증 부재

`04_2_notepad_server.py`는 `0.0.0.0`으로 열려 있어 **같은 네트워크 누구나 3000 포트로 접속 가능**하다. 정식 클라이언트(`04_1_notepad_client.html`)를 안 거치고도, 아무 웹사이트 콘솔에서 이 몇 줄만 쳐도 내 PC에서 메모장이 열린다:

```javascript
const s = new WebSocket("ws://192.168.0.160:3000");
s.onopen = () => s.send("open_notepad");
```

**증명된 것**:
1. "버튼을 눌러야만 실행된다"는 착각. 실제로는 **그 문자열을 아는 사람이면 누구나 실행 가능**.
2. 서버가 "누가 보냈는지"를 전혀 검증 안 한 게 핵심 구멍. 화이트리스트(뭘 실행할 수 있는지)는 있었지만, 인증(누가 실행시킬 수 있는지)이 없었다.

> 이게 "해킹의 기초" 느낌인 이유: **의도된 기능을, 의도되지 않은 경로로 실행시키는 것**이 많은 실제 취약점(임의 명령 실행·인증 우회)의 본질이다.

### 보안 체크리스트 (인지용)

| 계층 | 필요한 방어 |
|---|---|
| **인증(Authentication)** | 연결 시 토큰/비밀번호 검증 — 화이트리스트 안의 값이라도 아무나 못 보내게 |
| **암호화(wss://)** | 평문 `ws://` 대신 `wss://`로 도청·중간자 공격(MITM) 차단 |
| **입력 정제(Sanitization)** | `pc_type`처럼 내용이 자유로운 기능은 화이트리스트가 안 되니, 악성 패턴 필터·길이 제한 |
| **연결 범위 제한** | `0.0.0.0`(전체) 대신 특정 IP 대역·방화벽 제한 |
| **속도 제한(Rate Limiting)** | 짧은 시간 다수 명령 차단 |
| **로깅** | 누가 언제 무슨 신호 보냈는지 기록 — 추적 가능 |
| **최소 권한** | 서버를 관리자 권한으로 안 돌리기 (뚫려도 피해 범위 축소) |
| **위험 명령 2단계 확인** | "PC 종료" 같은 건 폰에서 한 번 더 확인창 |

`pc_type`은 **내용이 자유로워야 의미 있는** 기능이라 화이트리스트를 문자열에 적용 못 한다 → 이럴 땐 인증 토큰 + 입력 정제 + wss로 방어.

### 보안은 나중에 잡아도 되나 — Shift Left

"설계 단계에서 고려한다"와 "실제로 나중에 구현한다"는 다르다. 예를 들어 인증을 나중에 추가하면 **서버뿐 아니라 클라이언트도 같이 고쳐야** 한다(통신 규약 자체가 바뀜). 파일 2개일 땐 괜찮지만 버튼 10개로 늘어난 뒤엔 손댈 곳이 훨씬 많아진다.

| | 언제 |
|---|---|
| "인증이 필요하다"는 인지·설계에 자리 마련 | **처음부터** |
| 실제 코드로 촘촘히 구현·테스트 | 기능이 자리잡은 뒤 단계적으로 OK |
| "보안은 나중 문제"라며 생각조차 안 함 | ❌ 나중에 구조를 다시 짜야 할 수 있음 |

**Shift Left** = 버그·보안 문제는 늦게 발견할수록 고치는 비용이 커진다. 오늘 구현 다 끝난 뒤 "어, 뚫리네?"를 실습으로 겪은 게 정확히 이 패턴. 다행히 학습 단계라 비용이 작았을 뿐.

### 왜 같은 와이파이에서만 됐나 — 사설 IP

`192.168.x.x`는 **사설(로컬) IP** — 우리 집 공유기가 집 안 기기에 나눠주는 내부 전용 주소라 공유기 바깥(인터넷)에선 못 찾아온다("우리 아파트 몇 호"는 다른 아파트에선 의미 없음).

**나가는 것 vs 들어오는 것은 비대칭**:

| 방향 | 지금 가능? |
|---|---|
| 내 PC → 인터넷 (구글 검색, pip install) | ✅ 배포 안 해도 됨 |
| 인터넷 → 내 PC (데이터망 폰이 3000포트로 접속) | ❌ 안 됨 |

막힌 건 "내 PC가 인터넷에 요청 못 함"이 아니라 **"인터넷 쪽에서 내 PC를 못 찾아옴"**이다. 공유기의 **NAT**가 "우리 집 기기가 먼저 요청하면 답장은 들여보내주지만, 아무도 요청 안 했는데 밖에서 걸어온 낯선 연결은 막는다"는 규칙으로 동작하기 때문(방화벽·공유기에 내장된 최소 방어선). 인터넷에 공개하려면 **포트포워딩**(공유기가 문 열어줌)이나 **클라우드 배포**가 필요하고, 그 순간 "같은 와이파이"라는 물리적 보안벽이 사라져 화이트리스트·인증·wss가 필수가 된다.

### Windows 방화벽 — OS 레벨의 같은 원칙

파이썬 서버가 "밖에서 오는 연결을 받는 문을 열겠다"고 하면 Windows 방화벽이 "이 정체 모를 python.exe를 허용해도 되나?" 하고 막는다. 원래는 실행 시 확인 팝업이 떠야 정상이고, 무시하면 조용히 차단되어 수동 허용이 필요할 수 있다(Windows 보안 → 방화벽 및 네트워크 보호 → 앱 허용 → python.exe 개인/공용 체크). 화이트리스트·인증이 코드 레벨이라면, 방화벽은 그 앞단에서 "이 프로그램 자체가 외부와 연결될 자격이 있나"를 거르는 OS 레벨 방어다.

> 참고: python.exe를 통째로 허용하면 **파이썬으로 실행되는 모든 프로그램**에 예외가 열린다. "필요한 만큼만 허용" 원칙에서 보면 넓은 편이라는 점은 의식해둘 것.

## 7. 오늘 완성한 기능들

폰에서 확인한 것: **메모장 실행 · 크롬 검색 실행 · 볼륨 올리기/내리기 · 화면 캡처 · 미디어 재생/일시정지 · PC 상태(CPU/메모리) 실시간 표시 · 한글 문장 원격 입력**.

세 가지가 합쳐져야 "여러 기능을 가진, 여러 명이 동시에 쓸 수 있는, (지향점상) 안전한 원격 제어 시스템"이 된다:
1. **id로 확장 가능한 UI 구조** — 버튼마다 고유 `id`, JS `addEventListener`, 서버 `elif` 분기를 세트로 추가하면 기능이 계속 늘어남
2. **화이트리스트 조건문** — 정해진 신호만 정해진 동작으로
3. **비동기 서버** — 여러 명이 아무 때나 눌러도, 한 명 처리 중 다른 신호를 놓치지 않게

## 8. 느낀점 · 배운 학습법

- **"코드 읽기 → 결과 예측 → netstat·개발자도구로 직접 검증"** 흐름이 오늘 계속 반복됐다. 추측을 눈으로 확인하는 습관이 개념을 확실히 박히게 했다. (덮어쓰기 가설을 Messages 탭으로, 포트 점유를 netstat로, 취약점을 콘솔 주입으로 직접 증명)
- **비동기·웹소켓이 서버 운용에 핵심**이라는 걸 체감. "동시에 여러 일"을 서버 분리 없이도 해내는 제3의 길.
- **보안을 직접 뚫어보니** 왜 필요한지가 몸으로 이해됐다. "인증 없는 포트는 그냥 열린 문"이라는 감각.
- **하드코딩하지 않는 디테일**(파일 경로, IP, 명령 화이트리스트)이 사실 다 같은 철학 — "누가 언제 어디서 실행해도 동작하는 코드"라는 실무 감각.
- 트러블슈팅(채널 문제, IP 변경, Pillow 의존성)을 겪으며 **에러 메시지를 곧이곧대로 믿지 않고 진짜 원인을 파는** 법을 익혔다.
